# Lab 01 — Autopsy of a failed model launch

## 1. Scenario and business problem

**Lahore Retail Co.** has been scoring customer churn risk for months. On
11 August a new model version was promoted straight from a notebook. Eleven days
later a customer-success manager complained that "scores look wrong for
month-to-month plans". The team rolled back — and now wants to know what
happened, when it *should* have been caught, and which part of their process was
missing.

You are the engineer asked to write the post-incident report. You are given the
incident's monitoring snapshot and a sample of predictions.

**Business problem:** an ML system lost quality silently. The cost is not just
the bad scores — it is that *nobody could tell* until a human complained.

## 2. Skills practised

- Reading a time series of model-quality metrics and separating noise from trend.
- Distinguishing **technical** failures from **organisational** failures.
- Mapping a failure to a specific stage of the ML lifecycle.
- Writing a concise incident summary that names causes, not symptoms.

## 7. Setup and execution steps

**Step 1 — Generate the data.** Run the command in §5.
✅ **Checkpoint:** both CSV files exist and `metrics_snapshot.csv` has 61 lines
(1 header + 60 days).
*If it fails:* see [troubleshooting.md](troubleshooting.md) §1 — usually pandas is
not installed in the Python you are running.

**Step 2 — Answer the four questions in `timeline.md`.** Open the file and work
through its "Your task" list. Use pandas (§8 gives the exact analyses) or a
spreadsheet — the analysis method matters more than the tool.

**Step 3 — Quantify the detection gap.**

```python
import pandas as pd
m = pd.read_csv("metrics_snapshot.csv", parse_dates=["date"])
first_bad = m[(m.auc < 0.75) | (m.missing_rate > 0.03) | (m.drift_score > 0.15)]
print("promoted:", m.loc[m.model_version.eq("v3"), "date"].min().date())
print("first breach:", first_bad.iloc[0]["date"].date())
```

Expected: `promoted: 2026-08-11` and `first breach: 2026-08-14`.
✅ **Checkpoint:** the gap between those two dates is your *best-case automated
detection* delay; compare it with the human complaint date in `timeline.md`.

**Step 4 — Classify every timeline row.** For each row, assign exactly one
lifecycle stage from concepts §2 (data / validate & version / train & experiment /
evaluate / register & promote / package & deploy / serve / monitor / retire or
retrain) and one cause type (technical or organisational).

**Step 5 — Write the one-page post-incident report.** Structure:

1. What happened (3 sentences maximum)
2. When it should have been caught, and why it was not
3. Root causes — minimum three, each with its lifecycle stage
4. The single change that would have helped most, and why
5. What you would add to this system first (one item, justified)

**Step 6 — File your evidence.** Save the report and your analysis script/notebook
to `modules/01/` in your portfolio repository.

## 10. Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| `ModuleNotFoundError: pandas` | Wrong interpreter / no environment | `python -c "import pandas"`; see [troubleshooting.md](../../troubleshooting/index.md) §2 |
| File not found when running pandas | Wrong working directory | `Get-Location` 🪟 / `pwd` 🐧 — must be the `01-autopsy` folder |
| Only `v2` rows appear | Truncated file | Regenerate (step 1) |
| Your AUC numbers differ from §8 | Different file or edited data | Regenerate; the generator is deterministic (same seed) |
| You cannot decide a row's stage | Vague question | Ask "what would have prevented this?" — prevention names the stage |

Fuller list: [troubleshooting.md](troubleshooting.md) for this module,
