## Questions

**Q1.** Classify each as batch, online, or streaming: (a) nightly scoring of a
campaign CSV; (b) a fraud check on one transaction; (c) our `/predict` called
with 100 records; (d) weekly retraining on all history.

**Q2.** *(True/False + why)* "Online serving with 100-record batches is the
same as batch inference."

**Q3.** A caller sends `"contract_type": "lifetime"`. What status code
returns, *who* generates the body, and why does that never reach the model?

**Q4.** Contrast 422 and 503 in this service: what does each mean, who fixes
it, and what should the caller do?

**Q5.** Why is the model resolved once at startup rather than per request?
Give one benefit for **performance** and one for **operations**.

**Q6.** Your teammate wants `/health` to validate the model by scoring a
sample record. Argue against it in two sentences using this module's criteria.

**Q7.** Name two things FastAPI derives from the pydantic schema that a
hand-written Flask-style route would need manual code for.

**Q8.** State one thing your lab latency measurement does *not* prove, and
name the module that addresses it.

**Q9.** The service returns `503` with remediation steps instead of crashing
when no model exists. Who benefits — orchestrator, human, or both? Explain.

**Q10.** `/model-info` publishes `precision: 0.0`. Why is publishing it the
right design rather than a bug or something to hide?

## Answers

**Q1.** (a) batch · (b) online/streaming (per-event) · (c) online with batching
(one round trip, many records) · (d) batch (training, not inference at all).
*(5/5)*

**Q2. False.** Batch inference means *no request-response coupling*: data is
parked, scored in bulk, results consumed later — different failure modes,
latency budget, and operational shape. Our endpoint is still **online** (a
caller waits inside one HTTP request); batching *records* inside it is payload
design, not a change of serving paradigm. *(5/5)*

**Q3.** **422**, generated by the pydantic validation path in FastAPI
(our custom handler reformats it) — validation runs *before* the endpoint
function, so an illegal enum value never reaches the model code. *(5/5)*

**Q4.** **422** = the payload violates the contract → the *caller* fixes their
request (their bug). **503** = the service is live but cannot serve right now
(no model) → *you* fix the service; the caller should retry later or alert.
Conflating them would send operators chasing client bugs and vice versa. *(5/5)*

**Q5.** Performance: model loading is tens–hundreds of ms — per request would
dominate latency and destroy throughput. Operations: one process serves one
fixed model version for its lifetime, so promotions/rollbacks become explicit
restarts that monitoring and humans can see (concepts §5). *(5/5)*

**Q6.** A health check must be *cheap* and *stable* — scoring a sample couples
liveness to model/data state, so a bad data file would make the orchestrator
kill a healthy process (or mask real failures under slow probes). Quality
belongs in `/model-info` metrics and Module 14 monitoring, not in the liveness
path. *(5/5)*

**Q7.** Request **documentation** (`/docs`, OpenAPI schema) and **automatic
request parsing/rejection** (types, ranges, enums → 422) — plus response
models. Hand-rolled routes need annotation, manual parsing, and manual docs,
which then drift from reality. *(5/5)*

**Q8.** It does not prove behaviour **under concurrency/load**, nor network or
container effects — sequential local timings on an idle laptop understate real
serving. Module 16 covers load, scaling, and latency budgets. *(5/5)*

**Q9.** **Both.** The orchestrator gets a live-but-unready service it can
probe and retry (with `status: degraded` signalling readiness), while a human
gets actionable instructions instead of a crash loop — the best of liveness
and diagnosability. *(5/5)*

**Q10.** Because it is true: the model ranks (AUC 0.7163) but classifies
nothing positive at threshold 0.5. Hiding it would let a caller assume "0
errors = good classifier"; publishing it forces the threshold conversation
(the exact topic Module 14 monitoring is built to inform). *(5/5)*

Below 60: re-read concepts §1–§5 and re-run the suite verbosely.
