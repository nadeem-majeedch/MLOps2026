## Questions

**Q1.** Recite the 14-link capstone chain from memory. Which three links
are *refusal points* (gates), and what does each refuse?

**Q2.** Two engineers disagree: "MVP means lower quality." Using
concepts §3 and the rubric's hard conditions, rebut them in three
sentences.

**Q3.** Define **lineage** operationally: someone asks "what data produced
the model serving right now?" — write the exact chain of files/ids you
would walk in the reference implementation.

**Q4.** State an SLO for (a) the scheduled pipeline, (b) the API — one
sentence each, measurable *on a toy system*, with the window and the
measuring command.

**Q5.** Your CI is green but has never failed. What does the rubric
require you to demonstrate about your gates, and how would you show it
without merging broken code to main?

**Q6.** In the reference monitoring run, drift was **strong** on three
features and decision was **MONITOR**. Explain — with the numbers — why
"retrain now" would have been wrong.

**Q7.** The reference ships with fairness gap 0.1318 vs a 0.10 target.
Give both legitimate engineering responses, and name the one response
that is *not* legitimate.

**Q8.** You wrote "fully reproducible" but your clean-clone run required
one manual step. What is wrong, and what does concepts §8 say you do next?

**Q9.** Name two *rejected alternatives* from your own design document.
For each: the option, the deciding trade-off, and when you'd revisit it.
(No credit for strawmen.)

**Q10.** Design a fault injection for your capstone that is detected by
your tooling (not by watching), recovered only with documented commands,
and ends in a post-incident note. Which of the lab's four fault classes
did you pick, and what would catch it *earlier* next time?

## Answers

**A1.** 1 problem+criteria → 2 data provenance → 3 reproducible training →
4 split hygiene → 5 baseline+metrics → 6 tracking → 7 tests → 8
release+approval → 9 API → 10 container → 11 CI → 12 scheduling →
13 monitoring → 14 retrain/rollback (governance wraps all). The three
gates: **data validation** (refuses contract-violating input), **tests**
(refuses behavioural regressions), **quality/release gate** (refuses a
model below the floor — and, with fairness over target, requires a human
`--ack`). A chain without all three is a demo.

**A2.** MVP means *scoped*, not *weak*: the graded core must run, gate, and
reproduce on an ordinary machine — that is the *hard condition*. The
rubric caps you at Developing when reproducibility or quality gates miss,
so cutting those to chase extensions is precisely backwards. Extensions
add depth after the graded core is green (concepts §3's sequencing rule).

**A3.** `release.json` → `current` release id → `releases/<id>/` record
(`model_sha256`, `data_sha256`) → `artifacts/metrics.json` (same
`data_sha256`) → `data/support.csv` (regenerated by `generate_data.py`,
seed 20261026) → `runs.jsonl` entry (params, gate) → git commit containing
`config.yaml` + `src/`. Each hop is a stored hash or id — answerable from
files alone, in seconds (concepts §5).

**A4.** (a) "≥95% of scheduled pipeline runs complete green over any
24-hour window," measured by scanning `runs.jsonl`/scheduler history for
`gate_passed: true` ratios (command: your scheduled-run log query).
(b) "p95 `/predict` latency < 300 ms for 2-record batches over 100
sequential local calls," measured by your documented timing loop — local,
honest, and explicitly labelled as measured on one machine. Both need
window + signal + threshold; an unmeasurable SLO is decoration.

**A5.** The rubric requires that **at least one gate demonstrably blocks a
bad change**. Show it without dirtying main: a branch/PR that deliberately
degrades something (lower a test's subject, corrupt a fixture, or lower
the floor below the AUC), CI run captured showing red and the job that
failed, then delete the branch — the transcript is the evidence. Green
that has never been red proves nothing (Module 07).

**A6.** Three features moved strongly (PSI 0.8635 / 1.1786 / 0.4379) —
that is *input* movement. Measured AUC on the labelled shifted window was
**0.7712**, i.e. drop = **−0.005**: slightly *better* than the 0.7662
reference, above the 0.75 floor. Retraining on drift alone would have
replaced a good model based on a chart twitch — the decision matrix
requires drift **and** degradation to reach RETRAIN CANDIDATE. Drift says
the world moved; only labels say we got worse.

**A7.** Legitimate: (i) fix it — re-engineer features/threshold, re-measure
until within target before release; (ii) ship with **documented human
acceptance** — `--ack` reason, owner, mitigations, recorded in history —
plus a plan to revisit. Not legitimate: shipping *silently* (deleting or
ignoring the audit line), or lowering the target after seeing the number
to declare victory — changing the ruler to pass the test.

**A8.** "Fully reproducible" overclaims what you haven't demonstrated:
one manual step means the documented sequence is incomplete. Per concepts
§8, the fix is in the *documentation*, not the transcript: add the missing
step to the command list (or make the script do it), re-run the clean-clone
protocol, and only then restate the claim — with the tolerance declared
before the run.

**A9.** (Model answer shape — from the reference's own design.) *MLflow
server instead of `runs.jsonl`:* real option, rejected for the
service-process failure mode it adds; revisit at team scale or ~100s of
experiments. *Kubernetes for serving instead of one container:* real,
rejected because one machine cannot exercise the ops it simplifies;
revisit on real multi-node demand (Path A of Module 16 exists for the
mechanics). Your two must be *yours*, with all three properties.

**A10.** (Model answer, fault B.) Corrupt/raise the gate condition —
e.g. set `roc_auc_floor: 0.99` above the achieved 0.7662 — then run
`python pipeline.py`: the **gate stage refuses**, `report.md` records FAIL,
and CI's gate job would block the same state (detection by tooling).
Recovery: restore the config value (documented command), re-run, gate
green. Post-incident note: the injection cost one pipeline run; caught at
gate time — *earlier* catcher: a config-change check (diff the floor
against a documented policy) or a unit test asserting the floor equals the
agreed 0.75.
