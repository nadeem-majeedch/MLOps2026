# Worked example — the pipeline, observed

All output below is **actual** (`python -m pipe.run`, `examples/churn/`,
Python 3.14.7). Only the failing-floor value was set deliberately.

---

## 1. See the graph before running it

```powershell
# 🪟 from examples/churn
python -m pipe.run --list
```

```text
1. generate  <- (entry)
      out: data/raw/churn.csv
2. validate  <- generate
      in : data/raw/churn.csv
      in : config.yaml
      out: pipe_out/validate.json
3. features  <- validate
      in : pipe_out/validate.json
      in : config.yaml
      out: pipe_out/features.csv
4. train     <- features
      in : pipe_out/features.csv
      in : config.yaml
      out: pipe_out/model.joblib
      out: pipe_out/train_metrics.json
5. evaluate  <- train
      in : pipe_out/model.joblib
      in : pipe_out/train_metrics.json
      in : config.yaml
      out: pipe_out/evaluation.json
6. report    <- evaluate
      in : pipe_out/evaluation.json
      in : pipe_out/train_metrics.json
      out: pipe_out/report.md
```

Note `config.yaml` appears in four stages' inputs — changing one knob
legitimately invalidates everything that knob touches.

## 3. Tampered outputs are caught

Appending one line to `pipe_out/features.csv` by hand:

```text
[1/6] generate  SKIP  (up to date)
[2/6] validate  SKIP  (up to date)
[3/6] features  RUN   ... ok (0.07s)     <- outputs are hashed: bytes changed
[4/6] train     SKIP  (up to date)       <- regenerated bytes identical -> inputs unchanged
[5/6] evaluate  SKIP  (up to date)
[6/6] report    SKIP  (up to date)
```

The runner healed the file *and* correctly refused to retrain: the tampered
file re-generated byte-for-byte the same content. Determinism (concept §3) is
what makes this reasoning sound.

## 4. A real gate failure, and the resume

`config.yaml` temporarily changed to `roc_auc_floor: 0.99`:

```text
[1/6] generate  SKIP  (up to date)
[2/6] validate  RUN   ... ok (0.06s)
[3/6] features  RUN   ... ok (0.02s)
[4/6] train     RUN   ... ok (0.11s)
[5/6] evaluate  RUN   ... FAILED: quality gate failed: roc_auc 0.7163 < floor 0.99
[6/6] report    BLOCKED (upstream 'evaluate' failed)

pipeline FAILED at 'evaluate' - rerun the same command to resume from there.
EXIT=1
```

The manifest after that failure (`pipe_out/manifest.json`, extracted view):

```json
{
  "train":    { "status": "success" },
  "evaluate": { "status": "failed",
                "error": "quality gate failed: roc_auc 0.7163 < floor 0.99" },
  "report":   { "status": "success" }
}
```

(`report` still shows its *previous* success — it never re-ran. Stale success
plus a failed upstream is exactly why "BLOCKED" is printed at run time.)

Floor restored to `0.70`, same command again:

```text
[1/6] generate  SKIP  (up to date)
[2/6] validate  RUN   ... ok (0.02s)
[3/6] features  RUN   ... ok (0.02s)
[4/6] train     RUN   ... ok (0.15s)
[5/6] evaluate  RUN   ... ok (0.0s)
[6/6] report    SKIP  (up to date)       <- evaluation.json came back byte-identical
EXIT=0
```

`report` skipped even though `evaluate` re-ran — because the re-run produced
the same bytes. Signature comparison, not "did the stage execute".

## 5. Granularity: editing one function re-runs one stage

After changing only the text inside `report()`:

```text
[1/6] generate  SKIP  (up to date)
...
[5/6] evaluate  SKIP  (up to date)
[6/6] report    RUN   ... ok (0.0s)
```

Each stage hashes its **own source**, so a one-function edit invalidates one
stage — not the whole graph.

**Read the zero precision/recall honestly:** at the default 0.5 threshold this
logistic model predicts *no* churns (positive rate 0.09) — ROC-AUC still ranks
correctly at 0.7163. The same numbers appeared in Module 06; the threshold
question is deliberately parked for Module 14, where monitoring decides whether
it matters. A pipeline must report what happened, not what looks nice.
